# Rift compatibility — 2026-09-25

Checked from this machine against `http://rift.scylla-hammerhead.ts.net:8000` with `roncho::blocking::Client`, no `Authorization` header. Writes used workspace `roncho-test-<pid>` and the test deleted the session and then the workspace. `hermes-fleet` and `guardian-star` were not touched.

`GET /health` returned `200 {"status":"ok"}`. The body has no version. The image named in the Boxmaker requirements (`3.2.0-pr1092-7e57fe2`) was not confirmed by the server.

Where this disagrees with Honcho OpenAPI 3.2.1, rift wins:

- Conclusion `source_ids` may be `null`. 3.2.1 says an array, defaulting to empty for explicit conclusions.
- `POST .../conclusions/query` requires `filters.observer`/`observer_id` and `filters.observed`/`observed_id`. The 3.2.1 schema marks `filters` optional. The 422 body says both names are accepted.

## Questions

Checked again the same day against a second throwaway workspace, `roncho-q-20914`, then deleted. `DELETE` of that workspace afterwards returned 404. Reads of `hermes-fleet` and `guardian-star` were not made. Documentation cited below is Honcho's published v3 docs and OpenAPI 3.2.1. Where those and rift disagree, the rift result is the one to code against.

- **Q1** Calls with no `Authorization` header succeeded, including writes, so authentication was off on this listener. `POST /v3/keys` returned `405 {"detail":"Feature is disabled"}`, so this deployment will not mint a key. The published dashboard docs describe admin keys and keys scoped to a workspace, peer, or session, with peer-scoped keys limited to read-only access on sessions that peer belongs to. Whether this rift process can turn that on was not found.
- **Q2** A single message cannot be deleted here. `DELETE .../sessions/s/messages/{id}` returned `405 {"detail":"Method Not Allowed"}`. OpenAPI 3.2.1 has `GET` and `PUT` on that path and no `DELETE`. `PUT` with `{"metadata":{"label":"edited"}}` returned 200 and the following `GET` showed the new metadata and the original `content`. The published deleting-data page says peers and individual messages cannot be deleted, and that session delete is the way to drop a message. On rift, `DELETE .../sessions/s` returned `202 {"message":"Session deleted successfully"}`. The same page says the session is marked inactive immediately and that messages, embeddings, queued reasoning, session-scoped conclusions, and peer associations are removed in the background. An explicit conclusion created with `session_id: "s"` was still returned by `conclusions/list` in the request immediately after that 202. The page says explicit conclusions are removed with the session and derived ones (deductive, inductive, contradiction) survive because they have no owning session. That drain was not waited out, so "still present one request later" is all rift showed.
- **Q3** The published queue-status page says reasoning is not on the write path: messages are stored, then a background queue runs `representation` (the deriver), `summary`, and `dream`. `completed_work_units` counts work since the last cleanup, not lifetime totals. `GET .../queue/status?session_id=s` on rift, in the same second as two messages, returned `pending_work_units: 2`, `completed_work_units: 0`, `in_progress_work_units: 0`, and `sessions: null`. How long until a conclusion appears was not measured. The published reasoning-configuration page says `observe_me: false` on the peer stops Honcho observing that peer, and a session-level peer config overrides it. `observe_others` controls whether that peer forms a model of the others in the session. `reasoning.enabled` may be set on the message, the session, or the workspace, with the message winning. Those off switches were not exercised on rift. The peer was created with `configuration.observe_me: true`, and the response echoed that object.
- **Q4** On rift, message list and workspace search both honored metadata. `messages/list` with `{"filters":{"metadata":{"label":"keep"}}}` returned only the message that had that label. `search` with `{"query":"this","limit":10,"filters":{"metadata":{"label":"keep"}}}` returned that same message and not the other message, whose content also contains "this" and whose label was `drop`. The published filters page shows metadata equality and operators (`gt`, `gte`, `lt`, `lte`, `ne`, `in`, `contains`, `icontains`) plus `AND` / `OR` / `NOT` on list and search. It also says chat and representation filters accept only `session_id` (a string, a list, or `{"in":[...]}`) and reject other keys. A metadata filter was not sent to chat on rift.
- **Q5** OpenAPI 3.2.1 describes `source_ids` as the ids of other conclusions: premises for deductive, supporting conclusions for inductive, conflicting ones for contradiction, and empty for explicit conclusions, which come from messages rather than from conclusions. The conclusion object has no message-id field. On rift, an explicit conclusion came back with `source_ids: null` and `session_id: "s"`. A way to list the messages an explicit conclusion was drawn from was not found.
- **Q6** Rift returns 409 while any session is still active, with the detail quoted under O7. The published deleting-data page says there is no separate deactivate call: `DELETE` the session, which marks it inactive immediately and returns 202, after which workspace delete stops returning 409 even if the cascade is still running. `SessionUpdate` in OpenAPI 3.2.1 has `metadata` and `configuration` only, not `is_active`. That matches the earlier run, where delete-session then delete-workspace succeeded.
- **Q7** `GET /health` is the only health route in OpenAPI 3.2.1. Rift returns `200 {"status":"ok"}` and no version. No version route was found.
- **Q8** Further rift differences from the 3.2.1 document, beyond null `source_ids` and required conclusion-query filters: `POST /v3/workspaces`, `POST .../peers`, and `POST .../sessions` returned **201** on rift; the document says 200. `DELETE` session returned a JSON body `{"message":"Session deleted successfully"}` with 202; the document's success schema is empty. `POST /v3/keys` is in the document and returned 405 here (Q1). The image string `3.2.0-pr1092-7e57fe2` was still not present in any response.
